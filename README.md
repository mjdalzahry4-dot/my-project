# نظام إدارة مشاريع التخرج GPMS

تطبيق عربي لإدارة مجموعات ومشاريع التخرج، بواجهة ويب ثابتة وخادم Django REST Framework. الواجهة المنشورة على Netlify تتصل بخادم PythonAnywhere، وقاعدة البيانات الحالية SQLite. التغييرات المحلية الموصوفة هنا لم تُنشر بعد.

## تشغيل الواجهة التجريبية

```powershell
python -m http.server 8000 --directory frontend
```

ثم افتح <http://localhost:8000>. لتسجيل الدخول يجب تشغيل API أدناه.

## تشغيل خادم API محليًا

يتطلب Python وحزم `backend/requirements.txt`. أنشئ بيئة افتراضية وثبّت الحزم:

```powershell
py -m venv .venv
.venv\Scripts\python.exe -m pip install -r backend\requirements.txt
$env:DJANGO_SECRET_KEY = 'ضع-مفتاحا-محليا-عشوائيا-هنا'
$env:DJANGO_DEBUG = 'true'
.venv\Scripts\python.exe backend\manage.py migrate
.venv\Scripts\python.exe backend\manage.py createsuperuser
.venv\Scripts\python.exe backend\manage.py runserver 8001
```

أول حساب فائق يُنشأ بدور العميد، ويمكنه الدخول إلى لوحة الإدارة على <http://127.0.0.1:8001/admin/> وإعداد الأقسام والحسابات. تتوفر نقاط API على <http://127.0.0.1:8001/api/v1/>. انسخ `.env.example` كمرجع للمتغيرات؛ الإعدادات تقرأ من بيئة العملية ولا تحمل ملف `.env` تلقائيًا. استخدم SQLite الحالية؛ لا تضبط `DATABASE_URL` على قاعدة أخرى.

## النشر عبر GitHub وNetlify وPythonAnywhere

GitHub هو مستودع المصدر. ينشر Netlify الملفات الثابتة من `frontend/`، بينما يشغّل PythonAnywhere تطبيق Django مع ملف SQLite الحالي على نطاق `mjdkhaled1.pythonanywhere.com`. ملف `netlify.toml` يحدد مجلد الواجهة للنشر. إعداد `frontend/runtime-config.js` يوجّه طلبات الإنتاج إلى API المنشور على PythonAnywhere، ويستخدم منفذ التطوير المحلي فقط عند فتح الواجهة على `localhost` أو `127.0.0.1`.

على PythonAnywhere أبقِ قاعدة SQLite ومسار ملفها كما هما، واضبط المتغيرات من `.env.example` في ملف WSGI. لا ترفع ملف `.env` الحقيقي ولا تشغّل ترحيلات على قاعدة الإنتاج دون نسخة احتياطية قابلة للاستعادة.

إذا أردت استخدام PythonAnywhere لاستضافة الواجهة أيضًا، يمكن تقديم `frontend/` والخادم من أصل واحد؛ حينها يمكن إزالة أصل Netlify من `CORS_ORIGINS` بعد نقل الواجهة. دليل الخطوات التفصيلي في `DEPLOYMENT.md`. إعداد `render.yaml` يبقى بديلًا لـRender ولا يستخدمه مسار النشر هذا.

## الوظائف المتصلة والمتحققة

- نماذج وترحيل قاعدة البيانات للعلاقات والأدوار والطلبات ومراجعاتها والقرارات والمجموعات والمشاريع والعضويات والإسنادات والتسليمات والملاحظات والتدقيق والرموز وصندوق الأحداث.
- واجهات المصادقة برموز وصول، الأقسام، طلبات المجموعات، قرارات رئيس القسم، المجموعات والمشاريع وملاحظاتها وسجل التدقيق.
- صلاحيات حسب الدور والنطاق، تحقق من المدخلات، منع اسم المستخدم المكرر بعد التطبيع، منع عضوية الطالب في مجموعتين نشطتين، واعتماد ذري يتراجع بالكامل عند الفشل.
- الحسابات التي تنشأ بعد اعتماد الطلب تظل غير مفعلة حتى تعيين كلمة مرورها.
- الواجهة تسجل الدخول عبر رمز وصول مؤقت (12 ساعة)، وتحفظه في `sessionStorage` الخاص بعلامة التبويب وترسله في ترويسة `Authorization: Token ...`. تسجيل الخروج يبطل الرمز في الخادم، وتغيير كلمة المرور يبطل الرموز الحالية.
- إنشاء طلب المجموعة وإرساله لرئيس القسم، واتخاذ رئيس القسم قرار الاعتماد أو الإعادة أو الرفض ضمن نطاق قسمه، وقراءة/حفظ ملاحظات المشروع تتم على الخادم.
- يستطيع العميد إصدار رابط تفعيل أحادي الاستخدام للطالب؛ يعيّن الطالب كلمة مروره من الرابط خلال ساعة. ينسخ العميد الرابط ويسلمه يدويًا؛ لا تُرسل رسائل تحقق آلية.
- صفحة المواعيد تعرض المواعيد القادمة بحسب القسم ومشاريع المستخدم. يستطيع العميد ورئيس القسم الإنشاء والتعديل والحذف ضمن نطاق صلاحياتهما.
- يستطيع فريق الطالب حفظ رابط مستودع GitHub HTTPS لمشروعه وعرضه للمشرف والإدارة. تبقى صلاحيات المستودع وإدارته في GitHub.
- يستطيع الطالب رفع ملفات المشروع وتنزيلها، مع تحديد الملفات المرتبطة بمشروعه فقط.
- ينشئ اعتماد رئيس القسم سبع مراحل أساسية لكل مشروع. يستطيع المشرف ضبط العناوين والأوصاف والمواعيد، وإضافة مراحل مخصصة غير إلزامية، وتوزيع المهام على أعضاء المجموعة.
- يبدأ أعضاء المجموعة المراحل ويحدّثون التقدم، ويرسل قائد المجموعة المرحلة للمراجعة بعد ربط دليل ملفي بها. يعتمد المشرف المسند المرحلة أو يعيدها بملاحظات. يمنع الخادم بدء مرحلة مطلوبة قبل اعتماد سابقتها ويحفظ سجل الإرسال والقرارات.
- مركز إشعارات داخلي دائم يعرض عداد غير المقروء وإشعارات طلبات المجموعة والاعتماد والمواعيد وملاحظات المشروع وتغيير رابط المستودع وإرسال المرحلة ومراجعتها وإسناد المهام. تُحدّث الإشعارات أثناء بقاء الصفحة مفتوحة كل 30 ثانية، ويُخطر المشاركون عند إنشاء الموعد أو تعديله أو إلغائه. لا يرسل بريدًا أو SMS.
- يقفل الخادم الحساب النشط بعد خمس محاولات كلمة مرور خاطئة لمدة خمس دقائق، وينهي رمز الدخول بعد 15 دقيقة من عدم النشاط، ويسجل محاولات الدخول الفاشلة في سجل التدقيق.
- أنواع الملفات محددة بقائمة امتدادات مسموحة، والحجم الأقصى الافتراضي 10 ميغابايت ويمكن تغييره عبر `GPMS_MAX_UPLOAD_BYTES`. هذا لا يمثل فحصًا مضادًا للفيروسات.
- يسمح الخادم فقط بالأصول المدرجة في `CORS_ORIGINS`، ويقبل ترويسة `Authorization` لرمز الوصول. عناوين localhost متاحة في إعداد التطوير المحلي؛ أضف أصل الواجهة المنشور بدقة إلى `CORS_ORIGINS` في الإنتاج.

## نقاط API الأساسية

- `GET /api/v1/health/`
- `POST /api/v1/auth/login/` (يعيد `token` وبيانات المستخدم), `POST /api/v1/auth/logout/`, `GET /api/v1/auth/me/` (تتطلب `Authorization: Token ...`)
- `POST /api/v1/auth/password-reset-requests/`, `POST /api/v1/auth/one-time-password/{activate|reset}/`
- `GET /api/v1/departments/`
- `GET /api/v1/supervisors/`
- `GET /api/v1/users/`, `POST /api/v1/users/{id}/activation/` (العميد فقط، رمز تفعيل صالح لساعة ويعاد مرة واحدة)
- `GET|POST /api/v1/group-requests/`, `GET /api/v1/group-requests/{id}/`, `POST /api/v1/group-requests/{id}/submit/`
- قرارات رئيس القسم ضمن قسمه: `POST /api/v1/group-requests/{id}/{approve|return|reject}/`
- `GET /api/v1/groups/`, `GET /api/v1/groups/{id}/`, `GET /api/v1/projects/`, `GET /api/v1/projects/{id}/`, وملاحظات المشروع عبر `/api/v1/projects/{id}/notes/`
- رابط مستودع GitHub: `PATCH /api/v1/projects/{id}/repository/` (أعضاء المشروع من الطلاب فقط)
- المواعيد: `GET|POST /api/v1/appointments/`, `PATCH|DELETE /api/v1/appointments/{id}/` (القراءة بحسب القسم والمشروع؛ الإدارة للعميد ورئيس القسم)
- رفع ملفات المشروع عبر `POST /api/v1/projects/{id}/deliverables/` وتنزيلها عبر `/api/v1/deliverables/{id}/download/`
- مراحل المشروع: `GET|POST /api/v1/projects/{id}/stages/`, وتعديلها عبر `PATCH|DELETE /api/v1/project-stages/{stage_id}/`, وبدء/تقدم/إرسال/مراجعة المرحلة عبر `/api/v1/project-stages/{stage_id}/{start|progress|submit|review}/`.
- مهام المشروع: `GET|POST /api/v1/projects/{id}/tasks/`, وتحديث الحالة عبر `PATCH /api/v1/project-tasks/{task_id}/`.
- خطة المشروع: قائد المجموعة يرسل نسخ الخطة (المشكلة والأهداف والنطاق والمنهجية والأدوات وتوزيع المهام والجدول الزمني والمخاطر والمخرجات) عبر `GET|POST /api/v1/projects/{id}/plans/`، والمشرف المسند يراجع النسخة الأحدث عبر `POST /api/v1/project-plans/{id}/review/`. يمنع الخادم بدء أول مرحلة حتى اعتماد أحدث نسخة.
- لجنة الأفكار: يرشح رئيس القسم أعضاءها عبر `POST /api/v1/departments/{id}/project-committee/`، ويعتمد العميد التشكيل عبر `POST /api/v1/project-committees/{id}/approve/`. قائمة الأفكار للجنة عبر `GET /api/v1/project-idea-reviews/`.
- فكرة المشروع: قائد المجموعة يرسل نسختها عبر `GET|POST /api/v1/projects/{id}/ideas/`، ثم يراجعها المشرف عبر `/api/v1/project-ideas/{id}/supervisor-review/`، ويسجل كل عضو لجنة توصيته عبر `/committee-review/`، ويصدر رئيس القسم القرار النهائي عبر `/chair-review/`. لا تقبل الخطة ولا يبدأ التنفيذ قبل اعتماد الفكرة.
- جاهزية المناقشة: قائد المجموعة يقدم الملف النهائي والتقرير عبر `GET|POST /api/v1/projects/{id}/discussion-readiness/`. يتطلب الطلب اعتماد الفكرة والخطة وكل المراحل الإلزامية، ثم يراجعه المشرف ويحيله رئيس القسم أو يعيده.
- لجنة المناقشة: رئيس القسم يرشح عضوين نشطين أو أكثر ويحدد الرئيس عبر `POST /api/v1/defense-committees/` بعد إحالة الجاهزية؛ يعتمد العميد عبر `POST /api/v1/defense-committees/{id}/approve/`. `GET /api/v1/defense-committees/` يعرض الطلبات المحالة واللجان بحسب الدور. بعد الاعتماد يستطيع العضو تنزيل الملف النهائي والتقرير المعيّنين للجنة فقط.
- التقييم السري: يدير العميد المعايير وأوزان التقييم الجماعي والفردي عبر `GET|POST /api/v1/defense-rubric/` و`PATCH /api/v1/defense-rubric/{criterion_id}/`. يجب أن يبلغ وزن كل نوع 100% لاعتماد اللجنة، وتُحفظ لقطة المعايير ضمن اللجنة. يقدم العضو تقييمه الكامل عبر `POST /api/v1/defense-committees/{id}/evaluation/` ويقرأه عبر `GET`؛ لا تظهر تقييمات بقية الأعضاء قبل إكمال اللجنة.
- جلسة المناقشة: يحدد العميد أو رئيس القسم الموعد والمكان عبر `POST /api/v1/defense-committees/{id}/meeting/`؛ ويسجل رئيس اللجنة المحضر عبر المسار نفسه. أضيف مسار تعديلات ما بعد المناقشة: عضو اللجنة يسجل الملاحظة والطالب المكلف والموعد، والطالب يرسل دليل التنفيذ، والمشرف يراجع الأدلة والنسخة النهائية عبر واجهات `post-defense`.
- إدارة العضوية والإشراف: رئيس القسم يدير أعضاء المجموعة وقائدها عبر `GET|POST /api/v1/groups/{id}/members/` و`DELETE /api/v1/groups/{id}/members/{student_id}/` و`PATCH /api/v1/groups/{id}/leader/`. يعيد إسناد المشرف عبر `POST /api/v1/projects/{id}/supervisor/`، ويستطيع المشرف المسند الاعتذار عبر `/supervisor/decline/`. تحفظ الأسباب والتواريخ وسجل التكليف السابق.
- الإشعارات: `GET /api/v1/notifications/` و`POST /api/v1/notifications/{id}/read/`، مع عزلها بحسب المستلم.
- `GET /api/v1/audit-log/`

## التحقق الذي أُجري

بعد إعداد بيئة Python محلية، نُفذت أوامر فحص Django، والتحقق من عدم وجود ترحيلات ناقصة، وتطبيق الترحيلات على SQLite. لتشغيل اختبارات الخادم:

```powershell
$env:DJANGO_SECRET_KEY = 'مفتاح-اختبار-محلي'
$env:DJANGO_DEBUG = 'true'
.venv\Scripts\python.exe backend\manage.py test gpms
```

لاختبار تنبيه الواجهة عند انقطاع الاتصال أثناء استعادة الجلسة:

```powershell
node --test integration.test.cjs
```

راجع تقارير المراحل السابقة كسجل تاريخي؛ المرحلة الخامسة وصفت المصادقة بالجلسات قبل تحويل الواجهة والخادم إلى رموز وصول. دليل الإعداد الحالي في [التهيئة للنشر](DEPLOYMENT.md). لم تُختبر استعادة نسخة SQLite في هذه المراجعة، ولم تُنشر التغييرات المحلية الجديدة بعد.

## متطلبات لم تُنفذ بعد

- لا يوجد عامل يرسل البريد أو يعالج صندوق الأحداث؛ يصدر العميد رابط التفعيل ويرسله عبر قناة الجامعة. استعادة كلمة المرور بالبريد غير متاحة حتى ربط قناة توصيل آمنة.
- تخزين الملفات يستخدم إعداد Django الافتراضي، ولم يُربط بعد بتخزين إنتاجي دائم أو نسخ احتياطي. توجد قائمة امتدادات وحجم أقصى، لكن لم يُربط ماسح فيروسات ولا سياسة احتفاظ.
- نُفذ مسار الفكرة والخطة والمراحل والجاهزية، ثم لجنة مناقشة مستقلة يعتمدها العميد، مع حصر تنزيل الأعضاء على ملفات اللجنة وأدلة تعديلات ما بعد المناقشة. أضيف التقييم السري، وجدولة المناقشة ومحضرها، ومسار الملاحظات والنسخة النهائية، وإدارة عضوية المجموعة وإعادة إسناد المشرف مع حفظ السجل، ومؤشر النشاط التقني للأعضاء. يتضمن فحص الفكرة مقارنة لفظية أولية بأفكار المشاريع المكتملة فقط، ولا يثبت الانتحال ولا يرفض المشروع آليًا، ولا يعد بديلًا عن أرشيف أكاديمي بسياسة نشر. لم تُعتمد بعد آلية دمج درجات اللجنة ووزن المشرف؛ لذلك لم ينفذ إصدار النتيجة أو إغلاق المشروع والأرشفة. كما لم تنفذ النسخ الاحتياطية المؤسسية، وإعدادات الكلية، وبعض إجراءات تأهيل الطلاب.
- تتوفر تقارير XLSX للمشاريع والمجموعات والمشرفين والتقدم والمناقشات، وسجل العمليات للعميد فقط، مع نطاق يفرضه الخادم وفلاتر القسم والتاريخ. توفر الطباعة صفحة عربية يمكن حفظها PDF من المتصفح؛ لا يولد الخادم ملف PDF ثنائيًا بعد، ولا تصدر التقارير الدرجات السرية أو نتيجة نهائية غير محسوبة. بقيت إعدادات العميد الأكاديمية، والنسخ الاحتياطي المؤسسي ولوحة مسؤول النظام، والواجهة الثنائية اللغة.
- يستطيع الطالب تحديد الملف المرفوع كمشترك مع المجموعة أو شخصي؛ الملف الشخصي لصاحبه والموظفين المخولين، ولا يراه بقية الطلاب. تبقى ملفات المناقشة التي يختارها النظام متاحة لأعضاء اللجنة المعتمدة وفق نطاقها.
- ربط GitHub حاليًا يحفظ رابطًا فقط؛ لا يوجد GitHub App أو إنشاء مستودع أو قراءة نشاط المستودع.
- لا تزال بعض قرارات الجامعة مفتوحة في `ANALYSIS.md`، ومنها نطاق تفرد رمز المجموعة والحدود النهائية لحجم المجموعة. لم يُفرض نطاق تفرد للرمز بالتخمين.
- لم يُجر اختبار اتصال PostgreSQL أو إعداد إنتاج أو نشر أو اختبار أمني خارجي.

تُسجل بقية مراجعة التنفيذ في [تقرير مساحة العمل ودورة المراحل](STAGE8_REPORT.md). لم تُطبق ترحيلات هذه المرحلة على قاعدة الإنتاج ولم يُنشر التعديل.
